# Controlled V1 library import (schema / transform version 2)

This extends tools/migration-v1. It is not a synchronization service. A V2 quiz is an independent private copy. These commands require separate operator authorization before use against real projects. Development and CI use only synthetic fixtures, fakes and demo-* emulators.

## Source and target
Every cloud command requires --source-project and --target-project. The only accepted target is filmovy-kviz-v2-staging; source must be distinct and explicit. Hosting URLs, Firebase aliases and environment default project IDs are never used to select a cloud target. Cloud mode rejects emulator environment variables; existing emulator commands retain the exact localhost and demo-* requirements.

The source factory creates a separately named Firebase app and exposes only readLibrary/close. It queries library once with a field mask and projects the returned nested arrays before creating an artifact. Firestore masks cannot filter individual fields within an array of maps, so array elements are sanitized locally; no raw source document is saved. There are no source set/update/delete/batch/transaction operations. The target has a separate named app, credential and private collection adapter. Only export-cloud accepts source credentials; import never rereads V1.

Future credentials are explicit, separate service-account JSON paths outside Git, validated for the supplied project and service-account identity. No ambient ADC, Firebase CLI token, mutable default app or automatic IAM provisioning is used. No real key file is included/generated by this tool. The source identity must have read-only IAM (datastore.entities.get/list, conventionally roles/datastore.viewer); the target needs get/list/create for private import paths and datastore.databases.get as needed by the SDK. No target entity update/delete privilege is required. An operator must inspect inherited IAM grants too, and pass --confirm-source-read-only only after verification. A flag and project-bound key do not prove IAM permissions.

Server SDKs use IAM, not Firestore Rules. Firestore IAM can scope to a database; it does not provide the Security Rules collection-level read isolation assumed for browser clients. Use a dedicated short-lived operational identity with read-only database access, restrict code/network execution to this reviewed collection query, and disable its access after the export. If that database-level access is unacceptable, an authorized owner should prepare the sanitized export in a controlled read-only environment. Never test source permissions with a write. References: [Firestore IAM](https://firebase.google.com/docs/firestore/security/iam), [database IAM conditions](https://firebase.google.com/docs/firestore/manage-databases).

## Content allowlist
sanitize.ts defines the complete projection:
- Quiz: name/title/description/position/order, exactly one supported slides/quiz/items/questions array (also under data).
- Optional presentation settings: defaultAudioTrigger, scaleTitle, time_R1. Other settings are not inferred.
- Slides: title/text/type/roundHeader, options/optionsStr, correct/correctAnswer, moderator note, bgImage/answerImg/mediaRaw, videoStart/videoEnd/audioTrigger, bgOverlay/answerOverlay/qCount/bgRaw/id.
- Nested media: src/type only. Recap overrides: extraText/overrideMedia only.
- Answer/options values must be scalar or arrays of scalars. Unknown structured values in supported content fail closed.

The same projection runs before existing normalization and feeds legacy.raw / legacy.metadata. Arbitrary unknown fields, nested credentials and operational metadata are discarded; unsupported structured quiz content is rejected. Allowlisted free text remains quiz content, not an automatic PII detector: operator review is still necessary if personal data was manually placed in a question or note. Source timestamps are omitted from legacy metadata. The raw fields listed above preserve known presentation/diagnostic values; no V2 runtime reads an unrestricted raw object. Existing packages/quiz-domain/src/mappers.ts maps normalized/classified media, functions/src/editor/model.ts preserves private legacy extensions, and the migration maps the supported original presentation fields explicitly. No runtime extension requires unknown source keys.

Unknown slide types block cloud artifacts as UNMAPPED. The existing explicit pl representation is retained as the confirmed locked Pravda / Lež type. All slides, rounds, ordering and answers use the existing transform/validate pipeline. Answers exist only under private quiz slides/questions; quiz roots, journals, inventories and human reports omit their values.

### Observed nested source shape and nullable media

The bounded read-only source diagnostic confirmed `library/{id}` documents with `name` and a `data` map containing one ordered `quiz` array; optional presentation settings live at `data.settings`. That array is the global slide stream, including introductions, agenda, recap and end slides as well as questions. The existing `roundHeader` transitions derive rounds; extraction must not split or duplicate the stream.

Some slides explicitly store `media: null`, while others omit `media` or provide a `{ type, src }` map. The old sanitizer checked only for `undefined`, passed `null` to `pickScalars`, and failed in `object()` with `Expected quiz-content object.` This was an optional-field mismatch, not a different library hierarchy. The shared sanitizer now preserves this exact null marker in the allowlisted private legacy data. Existing media normalization already treats it as no nested media and still processes `mediaRaw` normally. Non-null scalar/array media, malformed roots, unknown significant types and missing answers remain blocked.

Both cloud extraction and managed-export/emulator normalization use this same sanitizer and transformation. No new data model, schema version, fingerprint algorithm, IAM capability or writer path is introduced. `test/fixtures/cloud-null-media.json` reproduces the observed structure with entirely synthetic content; its regression fails with the original sanitizer. Live diagnostics persist only structural types/counts. The repaired real exporter and staging import require a separate authorized run.

## Artifacts, provenance and fingerprints
Source artifacts are create-only local JSON under .local-data, marked read-only after creation. They contain sanitized schema-1 library content inside a schema-2 wrapper, exact source project/collection, export timestamp, counts, transform version and SHA-256 over canonical JSON. An existing file is never overwritten. File checks resolve symlinks/junctions; artifacts cannot escape .local-data. Protect this directory locally: the source artifact legitimately contains private answers. Reports contain only IDs, titles, counts, classifications and hashes, never answer values or source payloads.

Provenance extends the existing legacy object with source=v1, sourceProject, sourceCollection=library, sourceId, exportFingerprint and transformVersion; slides/questions include sourceSlidePosition. No second provenance tree exists. Quiz legacy.contentFingerprint is an audit hint: inventory recomputes the hash from actual root/slide/round/question content, never trusts the stored hash.

Content hashing canonicalizes object key order and sorts document arrays by stable ID while retaining positions in the hashed data. It excludes timestamps, actor stamps, revision and import provenance fingerprints. Prompt/answer/media/order/content edits change the hash. Export hash includes the export timestamp; content hash does not. Hashes detect alteration, not the identity of whoever approved a local artifact.

## Inventory and decisions
inspect-target-cloud reads only quizzes and their private slides/rounds/questions plus migrationV1Imports journals. listDocuments includes missing parent paths so incomplete imports are not mistaken for new data.
- NEW: no matching ID/provenance.
- IDENTICAL: exact source provenance and recomputed content match; zero writes.
- CONFLICT: proven provenance matches but actual content differs; zero overwrite.
- AMBIGUOUS: unknown provenance at the expected ID, alias/duplicate claims, or incomplete import; block.
- Other synthetic/unrelated quizzes remain unchanged.

Any conflict blocks the plan before the first write. Inventory and decisions are reread before import and each quiz. Conditional document creation closes existence races. Existing imports never receive set/merge/update/delete. Use a maintenance window preventing other tools from manufacturing new provenance aliases during import; create preconditions protect document paths, not arbitrary concurrent writes to a different ID.

## Atomic and multi-batch safety
Cloud validation rejects more than 400 source slides, matching functions/src/editor/callables.ts::maximumSlideCount. This keeps imported quizzes within the existing editor transaction contract; no runtime limit is raised.

Small quizzes use one atomic create batch. The implementation conservatively limits batches to 400 documents / 6 MB estimated JSON and individual documents to 800 KB; Firestore may reject tighter backend/index limits atomically. [Commit semantics](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/commit).

For larger quizzes:
1. Create migrationV1Imports/{quizId} with staging state and content hash.
2. Create private child documents in bounded batches; quizzes/{quizId} does not yet exist.
3. Read all children back and compare their full content hash.
4. Atomically create the quiz root and journal state/complete marker.

The existing runtime library queries root quiz documents, so an interrupted import has no library entry. There is no app/Rules change. The journal is denied by existing default-deny Rules, verified in Rules tests. Staff with a guessed private child path retain existing staff read rights; staging is not a new public surface. A failure leaves an immutable incomplete journal/children and blocks future attempts. There is intentionally no automatic resume, cleanup, overwrite or repair. Operator recovery of an interrupted import requires a separately reviewed task. Other completed quizzes remain valid; the entire dataset is not globally atomic.

## Two-phase operation
Build the existing tool first (pnpm --filter @filmovy-kviz/quiz-domain build, then pnpm --filter @filmovy-kviz/migration-v1 build). Commands below are templates; SOURCE_PROJECT and credential paths must be replaced using verified configuration. All outputs need fresh filenames.

A) Read-only export + inventory + dry-run:

    node tools/migration-v1/lib/cli.js export-cloud --source-project SOURCE_PROJECT --target-project filmovy-kviz-v2-staging --source-credential C:/protected/source-readonly.json --confirm-source-read-only --output .local-data/v1-content-import/source-export/library-v2.json
    node tools/migration-v1/lib/cli.js inspect-target-cloud --source-project SOURCE_PROJECT --target-project filmovy-kviz-v2-staging --target-credential C:/protected/staging-only.json --output .local-data/v1-content-import/target-before.json
    node tools/migration-v1/lib/cli.js dry-run-cloud --source-project SOURCE_PROJECT --target-project filmovy-kviz-v2-staging --input .local-data/v1-content-import/source-export/library-v2.json --inventory .local-data/v1-content-import/target-before.json --output .local-data/v1-content-import/dry-run-report.json

B) Explicit staging write from that approved export:

    node tools/migration-v1/lib/cli.js import-cloud --source-project SOURCE_PROJECT --target-project filmovy-kviz-v2-staging --target-credential C:/protected/staging-only.json --input .local-data/v1-content-import/source-export/library-v2.json --inventory .local-data/v1-content-import/target-before.json --validation .local-data/v1-content-import/dry-run-report.json --confirm-staging-write --output .local-data/v1-content-import/target-after.json

The source artifact is revalidated and transformation rerun. Plan and inventory must be internally valid, linked to the exact export, PASS and no older than 24 hours. The import re-inventories the live target; a stale claim of NEW cannot overwrite data. A safe second run using a fresh inventory/plan skips identical imports. Read-back verifies every imported quiz before proceeding. Read-only final inventory can be used for a later dry idempotence check.

Media classification is static only: legacy HTTP(S) images and YouTube references accepted by the shared editor parser are LEGACY; syntactically invalid references are BROKEN with warnings, other references UNSUPPORTED and blocking. OK is reserved for native supported media if a future approved import contract supports it; this version never creates owned Storage assets. Availability is UNVERIFIED; no crawler, download or URL rewrite occurs.
